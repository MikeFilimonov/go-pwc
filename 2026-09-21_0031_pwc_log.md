## Finished this session

**LIFO vs FIFO, locked in with justification (not just vocabulary):**
Traced `A → [B,C,D,E,F]` with `MaxPages = 6` under FIFO: fetched
`A,B,C,D,E,F` — every branch touched once, none gone deeper. Contrasted with
LIFO, which commits to depth immediately via whatever was pushed last, and
can exhaust a whole page budget on one branch (e.g. a 500-page chain) while
never touching sibling branches. Mike's own conclusion: **"With a page
budget, LIFO/DFS risks tunneling deep into one branch while starving the
rest, whereas FIFO/BFS guarantees broad coverage — every branch gets touched
before any single one gets gone deep into."**

**URL normalization / seen-set key — built up field by field, via
counterexamples, using `net/url.Parse` (not regex, not hand-scanning for
colons):**

- Key fields settled so far: **`Host` (lowercased) + `Path` (trailing slash
  stripped, except root `/` which stays `/`, since path length == 1 is the
  guard) + `RawQuery` (kept byte-for-byte, NOT lowercased) + `Scheme`
  (lowercased)**.
- `Fragment`: **dropped entirely** — never sent to the server, purely
  client-side ("scroll to element"), so `#a` vs `#b` is the same page.
- Rejected "lowercase the whole URL" via a Linux-filesystem counterexample
  (`/Products.html` vs `/products.html` could be two real, different files)
  — only `Scheme` and `Host` are conventionally case-insensitive; `Path` and
  `RawQuery` are server-defined and must be preserved as-is.
- Rejected "path alone is enough" via two counterexamples: (1) domain-zone
  crawling means `blog.site.com/products` and `shop.site.com/products` are
  both in-scope and are different pages — so `Host` must be in the key; (2)
  `/article?id=123` vs `/article?id=456` are different pages — so `RawQuery`
  must be in the key too.
- Important design decision, explicitly confirmed: **the normalized string
  is used ONLY as the internal seen-set key / comparison. The actual HTTP
  request is still made with the real, original, unmodified URL.** This
  separates "risk of bad dedup decision" from "risk of a mangled request."
- Scheme inclusion (`http` vs `https` treated as different by default)
  accepted as a reasonable default. **Parked for later, not resolved:** Go's
  `http.Client` follows redirects by default, and sites commonly
  301-redirect `http`→`https`, so the discovered `href` scheme and the
  scheme actually fetched can differ. Revisit when designing the fetch step
  (`resp.Request.URL` after redirects is probably the relevant tool).
