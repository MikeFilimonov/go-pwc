## Finished this stretch

**Package structure, concluded:** the orchestration loop (seen-set, queue,
the pop→fetch→extract→normalize→enqueue cycle) lives in `main.go`, not
inside `pages` or `links` — so neither of those two needs to import the
other. Mike's own parting instinct from the prior session ("we need a core
package with core types") led to concrete types, settled below, rather than
a separate orchestrator package.

**Core types — each one arrived at by rejecting a wrong version first:**
- **`Page{url, ancestor Page, descendants []Page}` — rejected entirely.**
  `ancestor Page` (a bare self-typed field, not a pointer) doesn't compile —
  invalid recursive type, since the compiler can't compute a finite
  `sizeof(Page)`. Mike correctly derived the fix (`ancestor *Page`) and then,
  pressed on *why* `[]Page` wouldn't have had the same problem, initially
  defended to pointers without knowing why; worked through it: a slice is a
  fixed-size header (pointer+len+cap) over a separately-heap-allocated
  backing array, so the recursion resolves at runtime, not in the type's
  compile-time layout — same reason pointers/maps/channels/funcs can all
  self-reference. But then the deeper question — does `Page` need
  `ancestor`/`descendants` at all — led to dropping `Page` as a type
  entirely: the stats spec (page count, total bytes, links found) only needs
  running totals accumulated once per page, never a per-page record you
  look back at, and nothing in the crawl loop walks up/down a page tree. A
  plain URL string is enough; no `Page` type needed.
- **`Stats` — kept**, exactly for those running totals. (Currently on disk as
  `PageCount int`, `TotalBytes int`, `LinksFound []string` — note
  `LinksFound` as a slice doesn't match the "running total" reasoning that
  justified `Stats` in the first place; worth revisiting whether that should
  be a count instead, next time stats are discussed.)
- **The queue item, `Item{Url string, Level int}` — settled.** Went through
  `map[*item]bool` (rejected: two different `*item` values for the same URL
  string are different pointers, so the map wouldn't dedupe at all — pointer
  identity isn't string equality) and `map[string]int` used as *both* the
  queue and the seen-set in one structure (rejected via an `A→[B], B→[A]`
  trace: if popping `A` means deleting it from the map, the seen-set loses
  the entry it must never lose; a seen-set and a FIFO queue are two
  different jobs with incompatible lifetimes).
- **The buffer (queue), `Buffer{Items []Item}` — settled.** Rejected
  `map[string]bool` as the buffer itself (no ordering, can't pop-front).
  Landed on a slice. Traced pop-by-reslice (`buffer[0]`, then
  `buffer = buffer[1:]`) against pop-by-index (`i < len(buffer)`), including
  whether reslicing actually frees memory (it doesn't — the backing array is
  shared until an `append` outgrows it; the two approaches are
  memory-equivalent, so the choice is readability, and reslicing's
  `for len(buffer) > 0` loop condition won out).
- **The seen-set, `PagesSeen{Elements map[string]struct{}}` — settled.**
  Key is the *normalized* URL string; value is `struct{}` once Mike
  recognized the question being asked is binary membership ("have I seen
  this?"), not "give me this URL's data back," so a zero-size value is
  correct, not `Item` or `bool`.
- **Marking timing — reconfirmed from the very first session's reasoning:**
  a URL is marked seen at *push* time, not pop time. Mike re-derived this
  himself when asked to re-trace the two-parents-share-a-child duplicate
  scenario.

**Resolving relative hrefs — the long-open gap finally closed.** Tested
"scheme + host + endpoint + params" against `about.html` (no leading slash)
discovered on `https://example.com/blog/post1.html`: naive scheme+host
concatenation gives `https://example.com/about.html`, but the correct
resolution is `https://example.com/blog/about.html` — Mike got this right
once forced to pick one and justify it. Conclusion: resolving a relative
href needs the base URL's *path* (specifically, proper relative-reference
resolution per RFC 3986 — handling `../`, empty hrefs, already-absolute
hrefs), not just scheme+host. Mike correctly chose not to hand-roll this and
will use `net/url`'s resolution function (hasn't tried it yet, but the
`ResolveReference`-shaped tool is the right category — don't be surprised if
he needs a nudge toward the exact method name next time, that's fine, he
found the *need* for it himself which was the actual point).

**The full per-link recipe, now fully ordered and correct, split into two
real steps:**
1. **Pop:** dequeue the front `Item` (already marked seen when it was
   pushed — the earlier draft that re-checked/re-added it to the seen-set
   *at pop time* was a regression Mike caught and corrected himself),
   then fetch its URL over the network. On fetch failure: **record and
   continue** — this matches the spec exactly. (Mike's first answer here was
   "retry," which doesn't match the spec; re-reading the spec himself, he
   corrected to record-and-continue, no retry.)
2. **Discover** (for every raw `href` found on the fetched page, using the
   popped item's own `Level` as the parent level):
   - resolve the href to an absolute URL against the current page's base
     URL (via `net/url`) — confirmed this must happen *before* normalization
     can run on it at all;
   - normalize the resolved URL into the seen-set key;
   - check the seen-set: if the key is already present, skip this href
     entirely; if not present, proceed;
   - new item's `Level` = `poppedItem.Level + 1` — **not** incremented from
     whatever was most recently pushed. Mike initially proposed "increment
     from the most recently enqueued item," which breaks on two sibling
     links discovered on the same page (`A→[B,C]`: by that rule `C` would
     wrongly inherit `B`'s level+1 instead of `A`'s). He then proposed
     storing a parent/ancestor reference on each item to fix it — caught
     himself that this is the same `Page.ancestor` idea already rejected
     earlier, and correctly concluded the parent's level is already sitting
     in the popped item in scope, no stored reference needed;
   - mark the key in the seen-set, then push `Item{resolvedUrl, level}` onto
     the buffer. (Still haven't explicitly discussed the `maxDepth` cutoff's
     exact placement in this ordered list — Mike mentioned checking it
     "before normalizing" in an earlier pass as an optimization, worth
     confirming that's still the intent next time, since the step list above
     doesn't explicitly re-state it.)
