## Spec (from mentor's roadmap, `Parallel Web Crawler.md`, pasted by Mike)

**Base:**
- Fetch via HTTP GET, http/https only; skip `mailto:`, `tel:`, `javascript:`.
- Only process `Content-Type: text/html`.
- Recurse up to `maxDepth`.
- Failures (404/timeout/DNS fail/500): record and continue, never abort.
- Filter links to same **domain zone** (`*.site.com` — subdomain-inclusive),
  not exact-host match. Not yet designed.
- Dedup: resolve relative hrefs against page base URL, strip `#fragment`,
  normalize trailing slash, lowercase host, drop default ports.
- Collect stats: page count, total bytes, links found.

**Advanced (not started):**
- Worker pool, bounded concurrency, graceful shutdown.
- Rate limiting: 5 req/s global, or 1 req/s/host; `time.Ticker` or token
  bucket.
- `context` for cancellation + ~30s overall timeout.

## Design decisions reached so far (via dialogue, all Mike's conclusions)

1. **`extractLinks(pageContent) → []string`** treated as a black box for now
   — HTML parsing is a separate concern, parked for later (will need
   `golang.org/x/net/html`, no regex — implementation note, not yet said to
   Mike explicitly).

2. **Seen-set = `map[url]struct{}`** (idiomatic Go set), not a count.
   Reasoning: traversal control only ever needs a yes/no "have I seen this,"
   never a frequency. A count (if ever needed) would be a separate stats
   concern, not part of the dedup/visited logic.

3. **Critical correctness fix — mark a URL seen at *enqueue* time, not at
   *fetch* time.** If marking only happens after a successful fetch, two
   different not-yet-fetched pages that both link to the same new URL could
   each enqueue it before either gets processed → duplicate. Marking at
   enqueue time also resolves failure handling for free: since a URL is
   marked exactly once regardless of outcome, a failed fetch just means
   "record it and move on" — no unmarking, no retries needed (matches spec's
   "log and continue" rule).

4. **To-visit-list (TVL) is a FIFO queue** — append to the end, pop from the
   front. Traced by hand on example graph `A→[B,C]`, `B→[A,D]` (A-revisit
   correctly skipped via seen-set), `C→[]`: fetch order came out **A, B, C,
   D** — breadth-first, level by level.

5. **Why FIFO/BFS over LIFO/DFS for a crawler** — mid-trace when session
   paused. Scenario given: seed `A → [B,C,D,E,F]`, but `B` leads into a
   50-page-deep chain `B→B1→B2→...→B50`. Question on the table: with a
   LIFO/stack, which of C/D/E/F get fetched before the B-chain is exhausted?
   Point to land: with a page budget (`MaxPages`), DFS/stack risks burning
   the whole budget going deep down one narrow branch while never touching
   the site's breadth; BFS/queue gives more representative coverage.
   **Mike had not yet finished this trace — pick back up here.**

6. **TVL items carry `(url, depth)`.** Depth is computed *per item*, from
   its specific parent's depth + 1 — Mike explicitly confirmed this over the
   alternative "one shared level counter, incremented once per fully-drained
   level" design.

7. **Depth type: plain `int`**, not `int8`/`uint8`. Reasoning: `cfg.MaxDepth`
   will come from `flag.Int` (so it's `int`); Go requires explicit
   conversions when comparing/mixing different-width int types; saving a few
   bytes per queue item isn't worth that friction for realistic depth values
   (3–10).

8. **Normalization is required before using a URL as a seen-set key or for
   domain matching.** Confirmed via concrete example: `http://EXAMPLE.com:80/products`
   and `http://example.com/products/` are different strings but the same
   page. Raw `href` strings are not safe to compare/key on directly.
